# 코드 검토와 런타임 최적화

2026-10-07 기준으로 `Assets/Scripts`의 던전·마을·입력·해체·저장·UI 코드와 `Assets/Editor`의 콘텐츠 생성·빌드 검증 코드를 검토했습니다. 프로파일링 도구의 소스·메타 파일·활성화 방식과 기존 측정 결과는 유지합니다.

## 수정한 위험과 중복

| 항목 | 변경 |
| --- | --- |
| 씬 사이의 개체 상태 | 프리팹별 풀을 추가하고 공격 타이머·조사 목표·순찰 경로·플레이어 참조·애니메이션 상태를 반환 시 초기화합니다. |
| 시체 저장 | 처리된 시체도 런 종료까지 소유합니다. 다음 대여가 기존 런의 저장 위치·해체 상태를 바꾸지 않게 합니다. |
| 던전 입장 검증 | 특정 던전 지정과 에디터 직접 실행도 카탈로그의 프리팹 등록을 검사합니다. 저장이 불가능한 설정으로 입장하는 상황을 방지합니다. |
| 로딩 중 요청 | 새 게임·불러오기의 중복 씬 전환을 거부합니다. 정상 이동 전에 개체를 반환하고 OnDestroy는 직접 씬 전환의 안전망으로 유지합니다. |
| 마을 UI | 판매·성장·의뢰 버튼이 포커스 이탈에 따른 GUI 입력 차단을 다시 활성화하지 않도록 이전 상태를 보존합니다. |
| 해체 | 큰 성공 영역도 막대 안에 배치하고, 지연된 프레임의 초과 이동량을 반사하여 포인터 속도를 유지합니다. 잘못된 난이도와 비정상 경과 시간을 방어합니다. |
| 자동 에셋 생성 | 파일은 존재하지만 타입을 읽지 못하는 설정을 기본값으로 덮어쓰지 않습니다. 문제를 기록하고 기존 파일을 보존합니다. |
| 중복 처리 | 일반 성공과 보급 도구 성공의 해체 완료 처리를 하나로 모았습니다. 가방·시체 복원의 중복 전리품 생성도 제거했습니다. |

주석은 풀의 소유권과 반환 순서, 이전 저장 호환, 공유 탐색 작업 공간, UI 캐시 갱신 조건처럼 코드만으로 의도를 알기 어려운 부분을 중심으로 추가했습니다.

## 몬스터·시체 풀

`DungeonActorPool`은 실제 프리팹을 기준으로 서로 다른 보관 목록을 사용합니다. 비활성 부모 아래 생성하고 런 데이터·시각 효과·플레이어 참조를 설정한 후 활성화합니다. 처음 필요한 인스턴스는 생성하고 이후 입장에서는 보관된 인스턴스를 우선 대여합니다.

대여 중인 인스턴스는 영속 풀의 자식으로 유지합니다. 던전 컨트롤러가 저장·귀환 정산 이후 반환하므로 씬 오브젝트 삭제 순서에 의존하지 않습니다. 마을에서는 비활성 캐시를 유지하고 메인 메뉴로 돌아가면 해제합니다. 이전 저장의 프리팹 ID 없는 생성 경로도 계속 지원하며, 이 경로의 오브젝트는 씬 이동 시 삭제합니다.

`Assets/Resources/DungeonTuning.asset`에서 다음 값을 조절합니다.

| Inspector 설정 | 기본값 | 의미 |
| --- | --- | --- |
| Pool Capacity Per Prefab | 32 | 프리팹 하나당 보관할 비활성 인스턴스 수 |
| Pool Total Capacity | 128 | 모든 종류를 합쳐 보관할 비활성 인스턴스 수 |

한도는 **활성 스폰 수를 제한하지 않습니다.** 반환 시 한도를 넘은 인스턴스는 비활성화한 뒤 삭제합니다. 한도를 0으로 지정하면 보관을 끌 수 있으며, 비교 측정에 사용할 수 있습니다. 처음부터 한도만큼 미리 생성하지 않습니다.

재대여 시 기본 Transform, 자식 활성 상태, 스프라이트·색·뒤집기·렌더러 활성, 콜라이더 활성과 물리 속도를 복원합니다. 시체의 해체 세션과 확정 전리품은 풀 밖의 새 `CorpseRunData`에 둡니다. 몬스터 능력치는 프리팹 또는 저장 스냅샷에서 독립적으로 복사합니다.

새 컴포넌트에 런별 상태·이벤트 구독·코루틴을 추가하면 `IDungeonPoolResettable.ResetForPool()`에서 정리해야 합니다. 상태 준비는 재사용마다 실행하는 초기화 메서드에 두세요. 프리팹 계층이나 컴포넌트 구조를 바꾼 후에는 Play를 다시 시작해 기존 인스턴스 캐시를 비웁니다.

## 메모리 할당을 줄인 부분

- 경로 탐색의 Queue·Dictionary·이웃 열거 객체를 최대 240칸의 재사용 배열로 대체했습니다. 탐색은 현재 Unity 메인 스레드에서 순차 실행하며 작업 공간을 비동기 작업에 공유하면 안 됩니다.
- 몬스터 시야 검사의 RaycastAll 결과 배열을 개체별 재사용 리스트로 바꿨습니다. 첫 확장 이후 용량을 재사용하며 고정 배열처럼 많은 충돌 결과가 잘리지 않습니다.
- 해체 소음은 현재 런의 몬스터 목록으로 전달하고, 탐색 기록은 플레이어가 다른 셀로 이동했을 때 갱신합니다.
- 몬스터 능력치 복사에서 JSON 왕복 문자열을 제거했습니다. 드롭 목록까지 독립적으로 복사합니다.
- 창고 UI는 변경 번호·검색어·정렬·선택 종류가 바뀔 때만 그룹과 가격별 수량을 다시 만듭니다. 반환되는 복사본으로 창고 원본을 수정할 수는 없습니다.
- 전리품 회전 미리보기는 클릭 시 계산하여 재사용합니다. 메뉴 문구 배열도 매 UI 호출마다 만들지 않습니다.
- 스프라이트 가공이 끝난 런타임 텍스처 사본의 CPU 픽셀 버퍼를 해제합니다. Resources의 원본 텍스처와 임포트 설정은 변경하지 않습니다.

## 검증 범위와 성능 판단

`./Tools/Validate-GameFlow.ps1 -CheckPlayerProtection -CaptureScreens`는 별도 프로젝트·저장 경로에서 실행합니다. 기존 암호화·저장 복원·경제·포커스·종료 회귀 검사에 풀 검사를 추가했습니다.

세 레이아웃에서 예열된 경로 리스트로 128회씩 탐색한 결과 관리 메모리 할당은 0바이트였습니다. 실제 Windows 플레이어에서 세 레이아웃 입장·귀환을 반복해 같은 인스턴스의 재사용, 저장 복원 시 공격·조사 타이머와 처리된 시체의 진행 유지, 새 입장 시 초기화를 확인했습니다. 맵 최대 수량인 몬스터 81마리·시체 82개가 서로 다른 셀에 생성됐으며, 귀환 시 두 종류의 프리팹별 한도에 따라 64개만 보관했습니다.

마지막 카탈로그 누락 방어까지 포함한 현재 코드로 `-CheckPlayerProtection`을 실행해 Unity 런타임 497개, Windows 비개발 Mono 플레이어 359개, 별도 프로세스 재실행 10개 검사를 통과했습니다. 직전 그래픽 검증에서는 런타임 485개·플레이어 361개·재실행 10개 검사를 통과하고 촬영 화면 14장을 확인했습니다. 런타임과 플레이어의 실제 스폰·의뢰 선택 등에 따라 개별 검사 횟수는 달라질 수 있습니다. 마지막 실행에서는 화면을 재촬영하지 않았으며 런타임·에디터·리소스·프리팹 파일이 검증 복사본과 일치하는 것을 확인했습니다.

이 결과는 **FPS 향상 비율이나 전체 게임의 무할당을 의미하지 않습니다.** 새 런의 전리품·세션·저장 데이터는 새로 만들고, 처음 필요한 인스턴스와 더 큰 경로·시야 리스트에는 할당이 발생합니다.

다음 성능 측정은 실제 목표 스폰 수와 배포할 아트에서 진행합니다. 풀 한도 0과 기본값을 비교해 첫 입장·반복 입장·귀환의 CPU 시간, GC.Alloc, 메모리 보관량을 측정하세요. 현재 바닥·벽은 씬마다 생성하므로 입장 지연에서 이 비용이 큰지 확인한 뒤 Tilemap이나 레이아웃 캐시 도입을 판단합니다. 몬스터 수가 증가하면 시야 검사·경로 재계산과 IMGUI 표시 비용도 함께 측정합니다. 기존 프로파일링 도구는 계속 사용할 수 있습니다.

풀 설계는 [Unity의 오브젝트 재사용 안내](https://docs.unity.com/en-us/engine/6000.6/manual/scripting/optimization/performance-optimizing-code-managed-memory/reusable-code)를 참고했으며, 현재 구현은 씬 간 소유권과 프리팹별·전체 보관 한도를 함께 관리합니다.
